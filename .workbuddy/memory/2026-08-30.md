## SideOfferTab 移动端优化（17:15–17:25）
用户反馈：右侧竖排 CTA（`src/components/SideOfferTab.astro`）在手机端随地址栏显隐
上下跳动；要求去掉 0.5s 延迟、打开即出现，并检查是否遮挡文章。

### 改动（4 处）
1. **去延迟**：`animation: sd-in .55s ... 0.55s forwards` → `0s`，打开网页立即出现。
2. **修跳动**：根因是 `top:50%` 的 fixed 元素锚在 **visual viewport**，地址栏收起时
   视口变高、中心下移 → 元素跟着上下窜。移动端（≤768px）改为
   `bottom: calc(1.5rem + env(safe-area-inset-bottom))` 下右锚定（地址栏变化发生在
   顶部，底部锚定几乎不受影响），并加 `right: env(safe-area-inset-right)`。
   桌面端保持垂直居中不变。
3. **不遮文章**：`global.css` 移动端给 `.container` 与 `.page-with-sidebars` 加
   `padding-right: max(var(--space-4), 48px)`，为 36px 宽的 tab 留右侧水槽。
4. **自动收起**：新增内联脚本（仅 ≤768px + `pointer:coarse` + 非 reduced-motion 生效）：
   默认完整展开让人看到优惠 → 4s 无交互后收起为 34px 小胶囊（仅留 logo）→
   hover/focus/touch 重新展开。带 `aria-expanded`。JS 失效时 CSS 兜底为完整展开。

### 验证（落在渲染后的 dist，非源文件）

### 🔴 iOS 补充修正（17:30，重要教训）
首版把移动端锚定到 `bottom: 1.5rem`，**对 iOS Safari 是错的**：
- **iOS 15+ 地址栏在屏幕底部**（~88px）；**Android Chrome 地址栏在顶部**。
- 底部锚定：Android 稳定 ✓，但 iOS 会 ① 被地址栏压住 ② 随地址栏收起而上下移动 ✗。
- 顶部锚定：反之。
→ **两端要求完全相反。fixed 元素只能锚视觉视口的某一端，纯 CSS 无法同时满足。**
  （`vh`/`svh`/`lvh` 都是相对视觉视口的固定值，解决不了——关键在锚哪一端，不在用什么单位。）
→ 最终解法：CSS 默认底部锚定（照顾 Android）；
  JS 用 UA 检测给 iOS 加 `.side-tab--ios` 切成 `top: 42vh`
  （iOS 视觉视口顶部不动 → 稳定）。降级安全：JS 失效则回到底部锚定。
→ 底部间距同时从 `1.5rem` 提到 `max(6.5rem, 15vh)`，确保不被 iOS 底部地址栏遮挡。
→ **教训：移动端任何 fixed 元素，都要先问"浏览器工具栏在哪一端"，再决定锚哪边。**

### 去掉缩进后的遮挡复查（量化，移动端 ≤640px）
CTA 宽 36px 常驻右边缘（覆盖屏幕右侧 36px）。各关键元素右边缘距屏幕右侧的距离：

| 元素 | 距右 | 与 CTA(36px) 关系 |
|---|---:|---|
| EndCTA 按钮（全宽） | 52px | 安全，余量 16px ✓ |
| InlineCta 按钮（全宽） | 40px | 不重叠，但**余量仅 4px**，视觉上贴着 ⚠️ |
| `.prose table`（display:block; width:100%） | 16px | **右侧 20px 被覆盖** ⚠️ 全站 96 页有表格 |
| 正文文字 | 16px | 右侧约 20px 被覆盖（已知，用户接受） |

- 计算依据：`.page-with-sidebars` padding 16px + EndCTA grid 16px + card 20px = 52px；
  InlineCta = 16px + 自身 padding 24px = 40px；表格 = 16px + 0 = 16px。
- **纵向滚动页面不受影响**（浏览器识别为 scroll 而非 click），只有 tap 落在覆盖区才误触。
- 表格被覆盖只在 CTA 所处的**纵向高度区间**内（Android 底部 15vh / iOS 顶部 42vh），非整页。
- 若日后要收紧：只改 InlineCta/table 自身 padding，**不要动正文容器**（两次否决的教训）。
